# Task Manager API

REST API для управления задачами 

## Как запустить

```bash
git clone https://github.com/Molark/task_manager
cd task_manager
docker compose up -d --build
```
Миграции подтягиваются сами при запуске Docker контейнера

После запуска:
- API доступен на `http://localhost:8000`
- База данных на `localhost:15432`

### Команды для работы с БД

```bash
# Миграции
docker compose exec app php bin/console doctrine:migrations:migrate --no-interaction

# Фикстуры (начальный статус "New" - он стоит по умолчанию для задач без статуса)
docker compose exec app php bin/console doctrine:fixtures:load --no-interaction

```

## Архитектурные решения и компромиссы

### 1. Связь Task и Status — ManyToOne
Задача имеет один статус, этот статус может быть у многих задач. Выбрано отношение `ManyToOne`.
### 2. Обработка удаления Status
Статус нельзя удалить пока к нему привязаны задачи, при попытке удаления вернется список связанных задач
### 3. Кастомный валидатор StatusExists
Вместо проверки существования статуса в контроллере или сервисе создан кастомный валидатор `StatusExists`. 
Это позволяет переиспользовать логику и держать валидацию в DTO. Также он отлавливается с помощью`EventSubscriber`

### 4. DTO для входных/выходных данных
Разделение на `InputDTO` и `OutputDTO` позволяет четко разделить контракты API и внутреннюю модель данных.

### 5. ResponseBuilder для единообразия ответов
Все ответы API формируются через `ResponseBuilder` что упрощает соблюдение единого формата и  кодов статуса.

### 6. Фабрика для создания сущностей
`Factory` инкапсулирует создание сущностей из DTO, и DTO из сущностей.

### 7. Разделение ответственности
Каждый класс служит своей цели и выполняет только свою работу, это позволяет масштабировать приложение и упрощает поиск ошибок.

### Что сознательно упрощено
- Нет аутентификации и авторизации
- Нет хорошей обработки ошибок - иногда приходят 500
- Нет кэширования
- Нет тестов
- Нет разделения на DTOFactory и Factory
- Не везде достаточный уровень абстракции
